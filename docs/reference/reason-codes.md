# Reason-code catalogue

Audience: operators, assessors, and contributors who read a report.
Purpose: list each reason code that the engine can write, where it comes from, and its effect on a step verdict.
Prerequisites: read the [verdict truth table](verdict-truth-table.md), section 1.

This page is generated by `uv run just reference`. Do not edit it by hand.

Engine version: `0.1.0rc1`. This page describes the source that generated it. That source can be later than the release with this version string. The section Unreleased of `CHANGELOG.md` records changes after the last release.

The page is built from the string literals in `src/dppce`. Docstrings and comments are not read.

The step verdict applies under the default verdict rules, where the call that produces the code fixes the execution status. "not fixed here" means that the generator cannot tie the code to a call that fixes the verdict. It does not mean that no verdict is fixed.

Some codes are not step reason codes. They are messages of the command line, the verifier, the timestamp commands, the migrations, and the authorization check.

Plan exclusions and retained problems also use codes that are not step reason codes.

The Check column names the registered check only where the check function itself writes the code. It is empty when a helper function writes the code.

A test purpose can change some verdicts with `verdict_rules`. Only an approved test method can make a missing answer fail. See the truth table.

A code with a run-time segment is listed once for each value of its closed set.

Lint findings such as `CAT019` are not reason codes. `dppce catalogue lint` reports them.

The last column comes from `dppce.report.hints`, the table that the HTML report uses. For a step that did not pass, it says what would make the step conclusive. For a failed step, it is the remediation. A step whose code has no entry gets the text of its execution status.
